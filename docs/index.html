Speed is what
you don’t do.

The expensive part isn’t always running the tool.
It’s asking what to do next. Again.

Sanborn is Laya plus the Rust harness—not a harness with an optional decision plugin. Its first runnable path keeps predictable work in Rust: permissions, scheduling independent reads, and executing explicit plans. The model produces plans, replans when needed, and returns for final verification.

Laya asks a typed question at each scheduling and evidence boundary and returns a bounded recommendation or explicit absence. It never grants execution authority. The current evaluator uses local evidence guards; a learned backend remains future work.

Conventional loop

Reason → Read → Reason → Read → Reason

Sanborn’s planned path

Reason → Laya + Rust execute a bounded plan → Verify with reasoning

Conceptual paths, not measured results. Fewer calls only help if the task still succeeds.

Initialize
Rust + Laya.

sb init prepares the harness and Laya together.
sb -p gives them work.

The first CLI is a Rust binary named sb. It needs Rust 1.88+ to install, an Azure deployment compatible with Chat Completions and function calling, and a credential provisioned through your environment or system keyring. Begin in a disposable workspace approved for that inference endpoint.

Init validates inference settings, confirms credential availability, and checks Laya’s Continue, Replan and Absent outcomes locally. It reads no workspace files. Networking is opt-in: --check-inference sends one synthetic chat probe. That confirms basic connectivity—not every tool or model capability.

Where setup lives—and what it never stores

Configuration is JSON at $XDG_CONFIG_HOME/sanborn/config.local, or ~/.config/sanborn/config.local when XDG is unset. On Unix the file is mode 0600. It stores the version, inference endpoint, deployment, API version and required Laya backend—not the API key. No workspace configuration file is created.

The key comes from AZURE_OPENAI_API_KEY or a Secret Service entry with application=sanborn and service=azure-inference. Linux keyring access uses secret-tool; environment configuration supports other platforms. Provision secrets through your secret manager, not CLI arguments, repository files or shell history.

For reasoning settings, precedence is CLI flags, Azure environment variables, saved configuration, then the endpoint keyring entry and deployment/API defaults. The defaults are gpt-5.4-mini and 2024-10-21; compatible deployments must be verified individually.

Repeated unchanged init is idempotent. Changing settings requires sb init --force; supply explicit settings because force rebuilds them from flags, environment/keyring and defaults. Failed checks leave configuration unsaved. Unsupported versions or Laya backends fail explicitly.

Existing environment/keyring-only runs still work before init. Laya remains required either way. Future model downloads, embedding or learned-backend prerequisites belong under sb init when implemented; none are performed by this first slice.

What exists today—and what does not

First runnable slice: sb -p, Azure reasoning, bounded plans, a required local Laya evaluator, parallel independent reads, ordered guarded writes, run limits and metadata events. A synthetic fixture exercises four tools with two reasoning calls.

Still proposed: learned decision inference and embedding, calibrated confidence, cache invalidation, streaming, independent acceptance certification and shell isolation. Laya currently uses exact local evidence guards—not a learned classifier or proven speed advantage.

The current path checks and policy flags are not an operating-system sandbox. Untrusted command execution needs separate isolation.

An instinct.
Not a second brain.

Ask a typed question. Get a bounded answer.
Or no answer at all.

Laya is a core decision layer, not an optional add-on. Its first pure-Rust evaluator checks local evidence guards. A learned backend and its embedding will be defined separately; Rust still enforces plan preconditions and permissions.

Every planned step records scheduling and evidence decisions. Compare future learned decisions in shadow mode before enabling them; calibrate thresholds on labeled fixtures, not marketing probabilities.

Continue

Only an explicit existing step. Dependencies and evidence hold. Permissions still apply.

↺

Replan

A tool failed, a guard did not match, or a dependency is unsatisfied. Return results to reasoning.

—

Absent

Insufficient evidence, such as truncated text. Record why and interrupt the plan—not bypass Laya.

sanborn-laya is a pure module: typed decisions, an engine interface and evidence guards. No HTTP transport or key storage belongs inside it. The current LocalLaya engine evaluates tool_succeeded, text_equals and text_contains. It reports no learned probability or calibrated confidence.

Rust checks evidence independently even when a decision engine recommends continuation. A faulty recommendation cannot satisfy a failed guard, authorize a denied tool or invent a step. Learned semantic decisions and their embedding will be evaluated separately before entering the normal path.

Execute a
guarded plan.

Validate the whole plan.
Authorize every step.

Azure submits one submit_plan call per reasoning turn. A plan contains up to 16 ordered steps: an ID, a registered tool, fixed JSON input, earlier dependencies and an evidence guard. Inputs cannot interpolate future tool outputs. If an edit needs unknown contents, inspect first, then request a new plan.

The scheduler batches consecutive independent reads with a ceiling of eight. Mutations remain ordered and serialized. A dependency becomes satisfied only after valid evidence and a matching Laya decision. On Replan or Absent, executed results and the interruption reason return to reasoning; remaining steps do not run.

Creation requires expected_content: null. Replacement requires the exact current contents and preserves existing permissions. Stale contents produce an explicit failure rather than overwriting blindly. There is no shell, delete or arbitrary command tool.

Run budgets, cancellation and filesystem limits

Defaults: 12 reasoning turns, 64 tool calls, 4,096 output tokens per model call, 60 seconds per inference request, 10 seconds per read tool and a 180-second execution deadline. Use --max-turns, --max-tool-calls, --max-tokens and --timeout to adjust bounded limits.

Ctrl+C cancels the run; completed writes are not rolled back. Blocking filesystem work can finish after cancellation. Writes are not individually timed out and replanned while their worker still runs. These are cooperative limits, not hard OS-level deadlines.

File tools reject workspace escapes, external or dangling symlinks and common credential-like paths. Hidden and ignored files are omitted from traversal. These are path and policy checks—not comprehensive secret detection, race-proof filesystem isolation or a sandbox for hostile tasks.

A completed plan is not a completed task. Reasoning returns to inspect results and request verification before its final answer. Exit zero means a final answer was returned without a runtime error; an external acceptance check must still establish correctness.

Feedback for
terminal people.

Color where it helps. Feedback while you wait.
No decorative inference calls.

Interactive stderr uses Crayon-inspired green/cyan markers and an ASCII | / - \ spinner with elapsed time. Waiting animation ticks eight times per second; events update immediately. The renderer uses the existing async runtime: no new thread, dependency, model request or artificial delay. It does not change Laya’s decisions.

--plain disables color and animation. NO_COLOR, even empty, disables colors but retains the interactive spinner. Pipes, TERM=dumb and JSON event mode disable both automatically. Active lines clear on completion, errors, deadlines and Ctrl+C; no alternate screen or hidden cursor is used.

Stdout contains the final answer or init result. Stderr contains progress or metadata-only JSON events: reasoning starts, accepted plans, Laya decisions, tool outcomes, durations and token usage. File contents and tool inputs are not logged in those events; the final model answer can still quote them.

The model can live elsewhere.
Control can’t.

Azure reasoning is connected.
That isn’t permission to send everything everywhere.

  1. Verify the endpoint

    The Azure adapter translates core messages, function calls, tool results, finish reasons and token usage to Chat Completions. HTTPS is required and redirects are disabled. Different deployments and provider protocols need their own compatibility checks.

  2. Approve the data boundary

    The prompt, tool schemas and selected tool results leave the machine. Start with synthetic fixtures; use only workspaces approved for the configured host. Personal infrastructure addresses, credentials and work data do not belong in public documentation.

  3. Separate decisions from reasoning

    The current Laya evaluator stays local. A future learned backend must preserve the typed contract and explicit absence behavior. A decision call must save more time than it adds without sacrificing acceptance success.

  4. Make failure visible

    Inference has bounded connection/request timeouts and response size. Malformed completions, refusals, inconsistent tool calls and HTTP failures are explicit errors. HTTP response bodies are not logged because they can echo inputs; automatic retries are not implemented.

Don’t count turns.
Count finished work.

The fastest wrong answer is still the wrong answer.

Use identical tasks, acceptance checks and reasoning models in isolated workspaces. Separate cold and warm runs. Compare the mechanism—not different hardware or an easier task.

What we have actually observed

End-to-end mechanism: an opt-in synthetic Azure fixture reads two files independently, writes an exact result, then reads it back through a dependency and text-equality guard. Acceptance checks assert the exact contents, four tool executions, eight Laya decisions and two reasoning calls. That shows plan execution without a reasoning call between every step—not a comparative speedup.

Terminal overhead: release-mode measurements observed about 0.18 µs per styled frame formatted to a sink, and 0.8 µs per frame written to a drained pseudo-terminal. Those are renderer microbenchmarks on one local setup, not screen-rendering, SSH or harness latency guarantees. Slow terminals can still add cost; --plain removes animation.

Failure coverage: offline tests exercise Azure wire translation and mocked HTTP, init persistence and failure behavior, Laya absence, faulty-engine guard rejection, dependencies, policy denial, read concurrency, serialized mutations, budgets, read timeouts, protected paths and guarded writes. Terminal checks cover pipes, JSON, no-color and cleanup.

No comparative speed benchmark yet. “Fastest” remains the ambition. Correct-result latency and acceptance success must establish the evidence.

The implementation
roadmap.

The first runnable slice is real.
The bigger proposal stays visible.

Implemented
sb init, sb -p, private user configuration, environment/keyring credentials, Azure chat reasoning, bounded plans, required local Laya, guarded file tools, terminal feedback and metadata traces.
Next evidence
Labeled decision fixtures and a comparison runner: expected results, failures, changed files and insufficient or misleading evidence. Measure acceptance success, total latency and decision overhead on identical tasks.
Learned Laya
Backend choice, embedding, semantic inference and confidence calibration remain undecided. Setup prerequisites will live under sb init. Future learned decisions need shadow evaluation before affecting the normal path.
Broader coding capability
Targeted edits, isolated commands and test-running tools are future work. The current CLI is a file-task harness, not yet a complete coding agent.
Runtime extensions
Invalidation-aware caching, streaming, context compaction, durable recovery and independent acceptance certification remain unimplemented.
