Speed is what
you don’t do.

The expensive part isn’t always running the tool.
It’s asking what to do next. Again.

Sanborn’s proposed fast path keeps predictable work in Rust: permissions, scheduling independent reads, and executing steps in an explicit plan. Reasoning stays with the model when the evidence actually changes.

Laya adds a typed question at the boundary. Not another paragraph. Not an agent with unchecked authority. A bounded recommendation—or an explicit absence.

Conventional loop

Reason → Read → Reason → Read → Reason

Proposed short path

Reason → Execute a bounded plan → Reason when needed

Conceptual paths, not measured results. Fewer calls only help if the task still succeeds.

One core.
Two instincts.

Execute what’s known. Reason about what isn’t.

What exists today—and what does not

Scaffolded: the core model/tool loop, provider and tool traits, policy checks, parallel consecutive read batches and ordered mutations.

Proposed: bounded plans, Laya routing, cache invalidation, Foundry adapters, acceptance checking and a complete runnable CLI. The workspace is incomplete and has not been validated as a working harness.

The current path checks and policy flags are not an operating-system sandbox. Untrusted command execution needs separate isolation.

Laya is a decision contract, not a confirmed installed model. A backend recommends whether new evidence needs reasoning. Rust still validates plan preconditions and permissions.

Start in shadow mode: record what Laya would choose while the normal loop stays in charge. Calibrate thresholds on labeled fixtures, not marketing probabilities.

The model can live elsewhere.
Control can’t.

Foundry servers are potential inference backends.
Not permission to send everything everywhere.

  1. Verify the endpoint

    Identify the server, model, protocol, authentication and structured-output support. “Foundry” alone does not establish compatibility.

  2. Approve the data boundary

    Start with synthetic fixtures. Work code and Qhipa wiki bodies must not leave the machine without recorded egress approval.

  3. Separate decisions from reasoning

    Use distinct provider contracts. A model may serve both, but a decision call must save more time than it adds.

  4. Make failure visible

    Bound retries and timeouts. Record fallback reasons. Keep keys outside source and sensitive payloads out of traces.

Don’t count turns.
Count finished work.

The fastest wrong answer is still the wrong answer.

Use identical tasks, acceptance checks and reasoning models in isolated workspaces. Separate cold and warm runs. Compare the mechanism—not different hardware or an easier task.
