Speed is what
you don’t do.

The expensive part isn’t always running the tool.
It’s asking what to do next. Again.

Sanborn is Laya plus the Rust harness—not a harness with an optional decision plugin. Its first runnable path keeps predictable work in Rust: permissions, scheduling independent reads, and executing explicit plans. The model produces plans, replans when needed, and returns for final verification.

Laya asks a typed question at each scheduling and evidence boundary and returns a bounded recommendation or explicit absence. It never grants execution authority. The current evaluator uses local evidence guards; a learned backend remains future work.

Conventional loop

Reason → Read → Reason → Read → Reason

Sanborn’s planned path

Reason → Laya + Rust execute a bounded plan → Verify with reasoning

Conceptual paths, not measured results. Fewer calls only help if the task still succeeds.

Initialize
Rust + Laya.

sb init prepares the harness and Laya together.
sb -p gives them work.

The first CLI is a Rust binary named sb. It needs Rust 1.88+ to install, an Azure deployment compatible with Chat Completions and function calling, and a credential provisioned through your environment or system keyring. Begin in a disposable workspace approved for that inference endpoint.

Init validates inference settings, confirms credential availability, and checks Laya’s Continue, Replan and Absent outcomes locally. It reads no workspace files. Networking is opt-in: --check-inference sends one synthetic chat probe. That confirms basic connectivity—not every tool or model capability.

Where setup lives—and what it never stores

Configuration is JSON at $XDG_CONFIG_HOME/sanborn/config.local, or ~/.config/sanborn/config.local when XDG is unset. On Unix the file is mode 0600. It stores the version, inference endpoint, deployment, API version and required Laya backend—not the API key. No workspace configuration file is created.

The key comes from AZURE_OPENAI_API_KEY or a Secret Service entry with application=sanborn and service=azure-inference. Linux keyring access uses secret-tool; environment configuration supports other platforms. Provision secrets through your secret manager, not CLI arguments, repository files or shell history.

For reasoning settings, precedence is CLI flags, Azure environment variables, saved configuration, then the endpoint keyring entry and deployment/API defaults. The defaults are gpt-5.4-mini and 2024-10-21; compatible deployments must be verified individually.

Repeated unchanged init is idempotent. Changing settings requires sb init --force; supply explicit settings because force rebuilds them from flags, environment/keyring and defaults. Failed checks leave configuration unsaved. Unsupported versions or Laya backends fail explicitly.

Existing environment/keyring-only runs still work before init. Laya remains required either way. Future model downloads, embedding or learned-backend prerequisites belong under sb init when implemented; none are performed by this first slice.

Check readiness offline with sb doctor

sb doctor checks workspace accessibility, saved configuration, credential availability, effective inference configuration and required Laya readiness. It makes no inference request, runs no workspace tools and writes no configuration. It accepts -w, inference-setting flags and --json.

The JSON report contains schema_version, ready, network_checked: false and all named checks. It prints no key or resolved endpoint. Exit zero means local checks passed; it does not prove authentication, function-call compatibility, egress approval or sandbox isolation. Use sb init --check-inference for an explicitly opt-in synthetic network check.

What exists today—and what does not

First runnable slice: sb -p, Azure reasoning, bounded plans, a required local Laya evaluator, parallel independent reads, ordered guarded writes, read-only tadpoles, shared inference budgets and metadata events. Synthetic fixtures exercise four tools with two reasoning calls, and a separate tadpole handoff with parent verification.

Still proposed: learned decision inference and embedding, calibrated confidence, cache invalidation, streaming, independent acceptance certification and shell isolation. Laya currently uses exact local evidence guards—not a learned classifier or proven speed advantage.

The current path checks and policy flags are not an operating-system sandbox. Untrusted command execution needs separate isolation.

An instinct.
Not a second brain.

Ask a typed question. Get a bounded answer.
Or no answer at all.

Laya is a core decision layer, not an optional add-on. Its first pure-Rust evaluator checks local evidence guards. A learned backend and its embedding will be defined separately; Rust still enforces plan preconditions and permissions.

Every planned step records scheduling and evidence decisions. Compare future learned decisions in shadow mode before enabling them; calibrate thresholds on labeled fixtures, not marketing probabilities.

↗

Continue

Only an explicit existing step. Dependencies and evidence hold. Permissions still apply.

↺

Replan

A tool failed, a guard did not match, or a dependency is unsatisfied. Return results to reasoning.

—

Absent

Insufficient evidence, such as truncated text. Record why and interrupt the plan—not bypass Laya.

sanborn-laya is a pure module: typed decisions, an engine interface and evidence guards. No HTTP transport or key storage belongs inside it. The current LocalLaya engine evaluates tool_succeeded, text_equals and text_contains. It reports no learned probability or calibrated confidence.

Rust checks evidence independently even when a decision engine recommends continuation. A faulty recommendation cannot satisfy a failed guard, authorize a denied tool or invent a step. Learned semantic decisions and their embedding will be evaluated separately before entering the normal path.

Execute a
guarded plan.

Validate the whole plan.
Authorize every step.

Azure submits one submit_plan call per reasoning turn. A plan contains up to 16 ordered steps: an ID, a registered tool, fixed JSON input, earlier dependencies and an evidence guard. Inputs cannot interpolate future tool outputs. If an edit needs unknown contents, inspect first, then request a new plan.

The plan schema now contains the actual registered tools and their typed inputs. Azure uses strict function calling with parallel_tool_calls: false; this limits model function calls, not Rust’s independent read concurrency or asynchronous Tadpoles. Azure’s schema subset does not enforce all numeric/text bounds, so Rust keeps enforcing the original limits and permissions. The deployment/API must support strict function calling: unsupported requests fail explicitly, without a silent non-strict fallback. Local doctor and a synthetic chat probe do not certify that compatibility.

The scheduler batches consecutive independent reads with a ceiling of eight. Mutations remain ordered and serialized. A dependency becomes satisfied only after valid evidence and a matching Laya decision. On Replan or Absent, executed results and the interruption reason return to reasoning; remaining steps do not run.

Independent investigations can be delegated to read-only tadpoles. They share the inference budget and return evidence to the parent, not permission to skip verification.

Creation requires expected_content: null. Replacement requires the exact current contents and preserves existing permissions. Stale contents produce an explicit failure rather than overwriting blindly. There is no shell, delete or arbitrary command tool.

Run budgets, cancellation and filesystem limits

Defaults: 12 reasoning turns, 64 tool calls, 4,096 output tokens per model call, 60 seconds per inference request, 10 seconds per read tool and a 180-second execution deadline. Use --max-turns, --max-tool-calls, --max-tokens and --timeout to adjust bounded limits.

Ctrl+C cancels the run; completed writes are not rolled back. Blocking filesystem work can finish after cancellation. Writes are not individually timed out and replanned while their worker still runs. These are cooperative limits, not hard OS-level deadlines.

File tools reject workspace escapes, external or dangling symlinks and common credential-like paths. Hidden and ignored files are omitted from traversal. These are path and policy checks—not comprehensive secret detection, race-proof filesystem isolation or a sandbox for hostile tasks.

A completed plan is not a completed task. Reasoning returns to inspect results and request verification before its final answer. Exit zero means a final answer was returned without a runtime error; an external acceptance check must still establish correctness.

Small workers.
One Sanborn.

Summon a tadpole. Give it a narrow question.
Let its croak bring the evidence home.

Tadpoles are Sanborn’s bounded, read-only subagents. The parent can plan summon_tadpoles for independent investigations, then compare and verify their findings. Each worker uses the same inference provider, workspace boundary and required Laya loop. sb init already prepares what they need.

In the illustration, warm paper scrolls carry Sanborn’s instructions out to the workers. Mint result packets bring their reports and evidence back. Each tadpole departs, investigates and returns on its own schedule: one croak can arrive while another worker is still investigating. Sanborn answers each arrival with a short frog croak, a buoyant hop, ripples and a “CROAR!” flash. Click Summon to unlock browser audio; use Croaks on/off to control it. The handoff is illustrative; the packets are not proof that a real task succeeded.

Summon

One to three independent objectives. Laya gates the parent’s schedule and each worker’s dispatch. Rust owns permissions.

Investigate

Every child plan passes Rust validation. Laya evaluates tool scheduling and evidence. Only registered read tools are available.

Croak

A bounded report with tool evidence, or an explicit blocker. The parent evaluates the findings and requests verification.

The model decides whether to summon; the prompt is not a guarantee of delegation. Worker IDs are unique across a run. Groups run concurrently inside a summon, but execute serially relative to the parent’s other tools. There is no separate child credential or Laya installation.

What a croak proves—and what it does not

returned means a worker’s model returned a report, not that its objective was proven. blocked carries an explicit runtime, Laya or deadline reason. Every croak is acceptance: "not_certified". Reports are untrusted evidence candidates, not new instructions or acceptance certificates.

Reports and evidence are bounded. Truncation is marked; evidence is explicitly omitted when combined serialized output exceeds the tool budget. The parent must inspect directly when needed. A worker may return prose explaining a blocker rather than fail at runtime; read its report, not just its status.

Requests reserve shared capacity before awaiting, including failures and cancellations. Observed JSON usage includes received child responses; missing usage is flagged with usage_complete. Failed or cancelled requests may still incur provider charges. Cancelling the parent drops child futures but does not guarantee remote inference or already-started reads stop immediately.

Small questions, explicit boundaries, evidence brought back. Tadpoles demonstrate bounded Laya-guided delegation—not a measured speedup or independent task certification.

A specialty is a contract.
Not a costume for a prompt.

Three built-in contracts start with known work in Rust: repository_scout, test_analyst and coder. The parent chooses the specialty explicitly. Each receives a fixed discovery plan before its first reasoning request; Laya gates every scheduled step and checks typed evidence. Rust independently validates the plan, permissions and guards.

Specialist contracts v1 · the baseline runs before reasoning
SpecialtyRust-authored baselineReasoning’s job
repository_scoutList the visible file structure within its directory scope.Interpret structure, inspect relevant manifests/source and cite paths. Separate observation from inference.
test_analystList files and search fixed heuristic test signals; independent reads can run together.Inspect relevant tests and report evidence-backed findings. No execution or measured coverage claim.
coderList scoped files; require observed file contents before proposing.Design one bounded replacement. Return a patch; only the parent can apply it.

scope is an enforced directory boundary, not a suggestion in a prompt. Specialists can only list, search or read inside it; coders additionally propose without writing. Unknown specialties are rejected; omitting the specialty preserves the ordinary general worker. The baseline consumes the existing child tool budget and uses the shared inference configuration.

The new discovery evidence guard checks structured file-list or search results. Limited or truncated evidence, and skipped search files, produce insufficient evidence; malformed results fail. Reasoning sees those outcomes and may interpret or replan, but final prose cannot turn an incomplete fixed baseline into a completed contract. Rerun with a narrower scope when needed.

Specialist croaks carry a versioned contract, baseline_complete and bounded observed facts with counts and samples. An incomplete baseline makes the croak blocked while retaining the model’s report. Completeness applies only to bounded visible discovery, not task acceptance. The analyst’s test markers are heuristic: no matches does not mean no tests, and no report measures coverage or proves tests passed.

This is the distinction we can demonstrate today: known first steps execute through Rust and Laya without a model planning turn; reasoning handles what still needs interpretation. Offline fixtures return both contracts after one reasoning call per child. That is mechanism evidence, not a representative speed benchmark or learned specialist routing.

Bring back findings.
Let Rust carry the quotes.

Scouts and analysts now have submit_findings: 1–6 structured findings with a unique ID, model-authored statement, observation or inference kind, workspace path and inclusive 1-based line range. Read the file first, inspect its contents, then submit a separate plan with guard: {"kind":"cited_findings"}. Statements are bounded to 512 bytes; IDs to 48 ASCII bytes; paths to 4,096 bytes.

Omit excerpt and Rust attaches the exact selected lines—up to 1,024 bytes, joined with LF without the trailing LF, with CRLF normalized. Supplied excerpts must match exactly. Rust checks prior successful reads, scoped paths and fresh whole-file contents; changed files require a new read. Laya gates the typed evidence, and Rust independently enforces it. The model chooses what a finding means; it does not need to retype the source.

The latest accepted submission from a completed plan appears in croak.findings with contract.citations_verified: true and claims_certified: false. This proves citation integrity at submission—not the truth of an interpretation, test execution or coverage. Missing, rejected, truncated or interrupted-plan findings remain unverified, even when a baseline-complete worker returns a confident report. Generic workers and coders do not receive this tool.

Define the subjects.
Not just the prompt.

A parent can declare citation_subjects on a scout or analyst: up to six fixed IDs, kinds, scoped paths and line ranges. The child reads the files, then submits a findings object keyed by those IDs, with statement only in each value. Rust attaches the immutable references and exact excerpts. Missing or extra subjects, attempted reference overrides and stale evidence fail; incomplete required subjects block the croak.

contract.citation_subjects_required and contract.citation_subjects_complete expose this completeness check. No declared subjects preserves flexible array findings and the existing baseline-based returned status. The subject set is the caller’s evidence requirement—not a claim that Rust understands the objective’s meaning.

Meet the specialists.
One fixture. Different questions.

Start with the synthetic greeting project in harness/examples/specialists. The scout maps its structure; the analyst inspects its illustrative test. Run either alone or summon both independently. The fixture deliberately has no Cargo manifest: the goal is inspection, not test execution.

The prompts now declare their citation subjects in structured summon input. The checker independently requires the expected full-file references, so silently changing a requested subject cannot pass as success.

Scout’s question

What exists, and what does each file appear to do? Look for cited paths to README.md, src/greeting.rs and tests/greeting.rs. Observed contents and inferred responsibilities should remain distinct.

Analyst’s question

What does greeting_contains_name actually assert? The test formats a string inline; it never calls the greeting function in src/greeting.rs. That is an evidence-backed limitation, not a measured coverage result.

Check the findings

The script requires accepted structured citations with unique IDs, expected paths, full-file ranges and exact excerpts. It checks the analyst’s inline-formatting evidence, guarded baselines before reasoning, complete received-response usage and unchanged fixture bytes. Missing findings or unexpected proposal/write tools fail.

Each run creates a temporary fixture, prints the structured final answer and checks metadata plus actual croaks with check.py. Nonzero exits and failed checks print diagnostics. These examples use real inference and may incur charges; model deviations or exhausted budgets can fail a run. PASS verifies these fixture-specific evidence requirements, not every sentence in the report or semantic correctness across arbitrary projects.

For a worker that proposes an actual change, continue with the coder example and exact-content check below. The scout and analyst examples never enable writes.

Coders bring back a patch.
Not permission to write.

A coding Tadpole can now inspect an existing file and propose a replacement. Its workspace remains read-only. The parent inspects the croak, decides whether to apply, and verifies the result. Laya gates the evidence at each boundary; Rust retains execution authority.

Inspect

Rust runs the scoped inventory before reasoning. The coder reads the target through read_file; the proposal must carry those exact observed contents, not an invented base.

Propose

propose_patch checks scope, observed contents, current contents and size without writing. The required patch_proposal Laya guard checks typed evidence. Both baseline and proposal must pass before application becomes available.

Apply & verify

The parent uses apply_tadpole_patch with the saved proposal ID. --allow-write and an exact old-content match are required. Stale files fail explicitly. The parent rereads the file; application is not proof of correctness or passing tests.

V1 is deliberately narrow: one existing-file replacement per worker, at most 8,000 bytes each for old and new contents. No new files, deletion, multi-file patches or command execution. A croak carries the replacement, proposal ID, byte counts and contract.proposal_complete; incomplete contracts remain blocked even if the report sounds confident.

Proposals live only within the run. An application attempt consumes its ID, including failures; inspect the error and summon a fresh worker. Parallel coders editing the same file do not merge automatically: after one applies, another based on stale contents must fail. These are optimistic content and path checks, not filesystem locking or an OS sandbox.

Try it. Check the actual file.

The repository includes a disposable synthetic example in harness/examples/coder. It starts with greeting.txt containing hello old\n, asks one coder to propose hello new\n, then asks the parent to apply and reread it. The script checks the exact file bytes itself, not the model’s final answer.

The script creates a temporary workspace, copies only the synthetic greeting fixture, runs sb with bounded calls, and cleans up afterward. It returns nonzero on a CLI error or mismatched file; a mismatch prints metadata events for diagnosis. Model behavior can vary—do not treat this expected output as a promised successful run.

What should happen inside the run?

  1. Inventory and read

    The coder’s Rust-authored baseline lists the fixture before reasoning. The coder reads greeting.txt; it still contains hello old\n.

  2. Return a proposal

    The coder submits propose_patch with the observed old contents and replacement. Laya checks patch_proposal evidence. The returned code-patch is a proposal, not a write.

  3. Parent applies and verifies

    The parent calls apply_tadpole_patch, then read_file with a text_equals guard. The script independently compares the resulting file with exactly hello new\n.

The offline regression covers missing reads, wrong old contents, scope escapes, protected paths, size limits, no-op changes, wrong guards, Laya rejection, incomplete baselines, absent proposals, denied writes, stale files and repeated application. The Azure test uses the same checked-in prompt and greeting as the runnable example, and asserts a returned coder croak, child proposal, parent application and subsequent read. These tests are run by you or the regression runner—not by a Tadpole. They do not certify unrelated code or coverage.

Feedback for
terminal people.

Color where it helps. Feedback while you wait.
No decorative inference calls.

Interactive stderr uses Crayon-inspired green/cyan markers and an ASCII | / - \ spinner with elapsed time. Waiting animation ticks eight times per second; events update immediately. The renderer uses the existing async runtime: no new thread, dependency, model request or artificial delay. It does not change Laya’s decisions.

-p - accepts piped or redirected UTF-8 prompts, preserving line breaks. Prompts must be nonempty, contain no NUL bytes and fit within 128,000 bytes. Interactive stdin is rejected; stalled pipes are bounded by --timeout before the separate task execution deadline begins.

--json emits one versioned final object on stdout: runtime status, final text, reasoning turns, tool count, token usage, agent duration, Laya backend and tadpole_croaks. Croaks come from actual nontruncated summon results, not model prose; no summons means an empty array. Successful results explicitly say acceptance: "not_certified". Runtime failures return a nonzero exit and a JSON error; argument-parser errors remain on stderr. JSON mode disables animation and color without changing execution.

Final tool counts and usage include tadpoles. inference_calls counts shared reserved requests; usage_complete flags whether all supplied response usage. Failed or cancelled requests may still incur provider charges. Runtime errors retain observed inference totals once initialized. Metadata events use summoned, tadpole with nested detail, and croak; terminal feedback shows Summoning and Croak markers without logging objectives or reports.

--plain disables color and animation. NO_COLOR, even empty, disables colors but retains the interactive spinner. Pipes, TERM=dumb and JSON event mode disable both automatically. Active lines clear on completion, errors, deadlines and Ctrl+C; no alternate screen or hidden cursor is used.

Stdout contains the final answer or init result. Stderr contains progress or metadata-only JSON events: reasoning starts, accepted plans, Laya decisions, tool outcomes, durations and token usage. File contents and tool inputs are not logged in those events; final text and structured croaks can contain source excerpts or patches. Treat stdout as potentially sensitive.

The model can live elsewhere.
Control can’t.

Azure reasoning is connected.
That isn’t permission to send everything everywhere.

  1. Verify the endpoint

    The Azure adapter translates core messages, function calls, tool results, finish reasons and token usage to Chat Completions. HTTPS is required and redirects are disabled. Different deployments and provider protocols need their own compatibility checks.

  2. Approve the data boundary

    The prompt, tool schemas and selected tool results leave the machine. Start with synthetic fixtures; use only workspaces approved for the configured host. Personal infrastructure addresses, credentials and work data do not belong in public documentation.

  3. Separate decisions from reasoning

    The current Laya evaluator stays local. A future learned backend must preserve the typed contract and explicit absence behavior. A decision call must save more time than it adds without sacrificing acceptance success.

  4. Make failure visible

    Inference has bounded connection/request timeouts and response size. Malformed completions, refusals, inconsistent tool calls and HTTP failures are explicit errors. HTTP response bodies are not logged because they can echo inputs; automatic retries are not implemented.

Don’t count turns.
Count finished work.

Use identical tasks, acceptance checks and reasoning models in isolated workspaces. Separate cold and warm runs. Compare the mechanism—not different hardware or an easier task.

What we have actually observed

End-to-end mechanism: an opt-in synthetic Azure fixture reads two files independently, writes an exact result, then reads it back through a dependency and text-equality guard. Acceptance checks assert the exact contents, four tool executions, eight Laya decisions and two reasoning calls. That shows plan execution without a reasoning call between every step—not a comparative speedup.

Tadpole handoff: a second opt-in synthetic Azure fixture summons two workers, checks each child’s Laya evidence events, and requires parent verification of both files. It asserts returned croaks, matching shared usage/tool totals, the inference ceiling and an unchanged workspace. Offline fixtures exercise permission rejection, Laya absence, deadlines and cancellation.

Contract-first specialists: offline fixtures assert that both discovery baselines precede the first child inference call, enforce directory scope, reject unknown roles and keep incomplete evidence blocked even under a faulty Laya recommendation. A separate opt-in synthetic Azure fixture checks both specialist baselines and their Laya events before child reasoning.

Terminal overhead: release-mode measurements observed about 0.18 µs per styled frame formatted to a sink, and 0.8 µs per frame written to a drained pseudo-terminal. Those are renderer microbenchmarks on one local setup, not screen-rendering, SSH or harness latency guarantees. Slow terminals can still add cost; --plain removes animation.

Failure coverage: offline tests exercise Azure wire translation and mocked HTTP, init persistence and failure behavior, Laya absence, faulty-engine guard rejection, dependencies, policy denial, read concurrency, serialized mutations, budgets, read timeouts, protected paths and guarded writes. Terminal checks cover pipes, JSON, no-color and cleanup.

No comparative speed benchmark yet. “Fastest” remains the ambition. Correct-result latency and acceptance success must establish the evidence.
